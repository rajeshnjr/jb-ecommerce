Playwright TypeScript: POM & Custom Fixtures

Using Playwright's Custom Fixtures to automatically initialize our Page Object Model in every test context.

1. fixtures/page-fixtures.ts

import { test as baseTest } from '@playwright/test';
import { GoogleSearchPage } from '../pages/GoogleSearchPage';

type MyFixtures = { googlePage: GoogleSearchPage; };

export const test = baseTest.extend({
  googlePage: async ({ page }, use) => {
    const googleSearch = new GoogleSearchPage(page);
    await googleSearch.navigate();
    await use(googleSearch); // Yields POM to test
  },
});
export { expect } from '@playwright/test';

2. tests/search-validation.spec.ts

import { test, expect } from '../fixtures/page-fixtures';

test('Test Case 1: Search for Facebook', async ({ googlePage }) => {
  await googlePage.searchFor('Facebook');
  await expect(googlePage.page).toHaveTitle(/Facebook/i);
});

Advanced Playwright Concepts & Troubleshooting

1. Where do we use Promises in Playwright?

Because Playwright operates via a WebSocket connection to the browser out-of-process, every API call is asynchronous and returns a Promise. You use promises in three main ways:

  • Sequential Actions: Using await on locators (e.g., await page.click('#btn')).
  • Handling Race Conditions: Storing a promise before triggering an action to wait for a network response or new tab.
  • Parallel Execution: Using Promise.all() to run multiple independent checks concurrently.
// Example: Awaiting a network response triggered by a click
const responsePromise = page.waitForResponse('**/api/v1/users');
await page.getByRole('button', { name: 'Submit' }).click(); // Action
const response = await responsePromise; // Resolve Promise

2. How do we test with specific browsers (Channels)?

By default, Playwright uses open-source Chromium, Firefox, and WebKit binaries. If you need to test against branded, installed browsers like Google Chrome or Microsoft Edge, you use the channel property in your playwright.config.ts.

// playwright.config.ts
export default defineConfig({
  projects: [
    {
      name: 'Google Chrome',
      use: {
        ...devices['Desktop Chrome'],
        channel: 'chrome', // Uses branded Google Chrome
      },
    },
    {
      name: 'Microsoft Edge',
      use: {
        ...devices['Desktop Edge'],
        channel: 'msedge', // Uses branded Microsoft Edge
      },
    },
  ],
});

3. If a test is working locally but not in CI, what do we check?

This is the most common QA challenge. If it works locally but fails in CI (Jenkins, GitHub Actions, GitLab), check these top culprits:

  1. Missing Dependencies: CI machines are blank slates. Ensure you are running npx playwright install --with-deps in your CI pipeline.
  2. Headless Mode Quirks: Tests run headed locally but headless in CI. Headless browsers don't render visually, which can break viewport-based locators. Test locally in headless mode (npx playwright test --headless) to replicate.
  3. Speed & Networking: CI machines are often slower or share network resources. Remove hardcoded page.waitForTimeout() and replace them with dynamic waits like page.waitForResponse() or expect(locator).toBeVisible().
  4. Viewport Size: CI defaults to 1280x720. If your app becomes responsive/mobile at that size, buttons might be hidden behind hamburger menus. Set a fixed viewport in your config.
  5. Debugging: Always configure your config to retain traces on failure: trace: 'retain-on-failure'. View the CI trace to see exactly what the browser saw.

4. Custom line to retrieve the latest release Playwright version

You can fetch the absolute latest version available on the NPM registry using standard node commands in your terminal:

# Get the latest version number from NPM
npm show @playwright/test version

# Check the exact version currently installed in your local project
npx playwright --version

5. How do we test Accessibility (a11y) with Playwright?

Playwright officially integrates with Axe (the industry standard accessibility engine) via the @axe-core/playwright package.

npm install -D @axe-core/playwright
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('Accessibility check on Dashboard', async ({ page }) => {
  await page.goto('https://example.com/dashboard');

  // Run the Axe accessibility analysis on the current page
  const accessibilityScanResults = await new AxeBuilder({ page }).analyze();

  // Assert that there are no violations
  expect(accessibilityScanResults.violations).toEqual([]);
});

Selenium + Pytest: Reusing conftest.py Fixtures

Using Pytest's yield keyword to initialize the Selenium WebDriver and Page Object, pass it to the test, and tear it down automatically.

conftest.py

import pytest
from selenium import webdriver
from pages.google_page import GooglePage

@pytest.fixture(scope="function")
def google_driver():
    driver = webdriver.Chrome()
    google_search_page = GooglePage(driver)
    google_search_page.navigate()
    
    yield google_search_page
    
    driver.quit()
